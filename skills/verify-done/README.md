# Completion Verification

**Evidence before the claim. If the command that proves it has not been run,
the claim cannot be made.**

## Running it

This is a specification an agent executes, not a binary. Install it by copying
this folder into your project's skills directory:

```bash
cp -r verify-done /path/to/your-project/.claude/skills/
```

Then invoke it:

```
/verify-done

or: "is this actually done?"
```

The agent reads [SPEC.md](./SPEC.md) and does the work. The `npm test` and
`pytest` calls in the spec are your own runners, and those are real.

**Working by hand:** read [SPEC.md](./SPEC.md) and follow it directly.
[CUSTOMIZE.md](./CUSTOMIZE.md) is where you bind the command set and the proof
table to your project.

## What it does

Five steps, in order: name the command that proves the claim, run it fresh and
in full, read the exit code and the counts, compare the output to the claim, and
state the claim with its evidence or the real status with its evidence.

Then it stops. It reports; it does not fix. That separation is deliberate:
anything that can edit the code can make the check agree with it.

## Who uses it

- **Engineering leads** who keep receiving "done" and finding it is not
- **Teams running coding agents**, where a completion report is generated by
  something with an incentive to look finished
- **Anyone running an autonomous fix-and-recheck loop**, which needs a cap more
  than it needs another retry
- **Solo builders**, where there is no second person to catch an unverified
  claim before it reaches a customer

## What it will not do

It cannot tell you the tests test the right thing, catch a flake from one green
run, or know about a CI job your command list omits. The Limitations section in
[SPEC.md](./SPEC.md) is the honest list, and it is worth reading before you rely
on this.

## The idea in one table

| Claim | Proof | Not proof |
|---|---|---|
| Tests pass | Full runner output, 0 failures, exit 0 | A run from before the last edit |
| Bug fixed | The original symptom, reproduced, now passing | The code changed and looks correct |
| Deployed | The endpoint answering correctly | A successful infrastructure apply |
| Agent finished | `git diff` showing the change | The agent's own report |

Each proof is one layer more concrete than what people substitute for it.
